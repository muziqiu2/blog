## 前言

我的站点分散在三家 CDN 上：Cloudflare 顶着大头，腾讯云 EdgeOne 承载主力域名，阿里云 ESA 上还有一个边缘小站。三家各有一个控制台，各说各的方言——腾讯叫「出流量」，阿里叫「Traffic」，Cloudflare 干脆只有 GraphQL；命中率一个按请求算、一个按字节算；阿里基础版最多让你查 7 天，腾讯能给 30 天。

每天想知道「我的流量跑到哪了」，得开三个网页、在脑子里做三次单位换算。这种事一旦开始忍受，就说明该动手写个东西了。

于是有了这个 CDN 管理面板：**一个窗口看三家，每 5 分钟自动采集，页面上所有数字都能和厂商控制台对上账**。整个系统是 Laravel + SQLite，跑在一台宝塔机器上，单用户、自用。它有一条不可动摇的底线：**只读**。所有适配器只调查询类接口，绝不操作 CDN 解析和配置——面板存在的意义是「看清」，不是「碰」。

![](/img/posts/cdntool/dashboard.webp)

这篇文章记录它是怎么长出来的，以及比「做功能」难得多的部分：**让每个数字都是对的**。截图里的数据时点为 2026-09-25 下午，会随时间变化。

## 三家 SDK，三种脾气

接入的第一课是：**厂商文档说的和你账号能用的，经常不是一回事**。

### 阿里：EA 不是那个 EA

我最早接的是「阿里云 EA」。代码写完，账号里查出 0 个域名——因为我调的是老版 CDN API（`cdn.aliyuncs.com`），而我账号里根本没那个产品。真正在用的是 **ESA（边缘安全加速）**，端点在 `esa.cn-hangzhou.aliyuncs.com`。一个字母之差，整个适配器推倒重来。

ESA 的 SDK 又是一番折腾：官方新版 typed SDK 依赖和 Laravel 9 锁定的 psr7 版本冲突，装不上；最后用的是官方 V2 通用客户端（`darabonba-openapi`），可以调任意 action，代价是没有类型提示。实测里还攒了两条铁律：

- **RPC 风格的请求 method 必须 GET**，用 POST 直接 403，不解释；
- 计量接口的 `Fields` 参数**必须是 JSON 字符串**，而且每次只允许**单 FieldName + 单 Dimension**，多传一个就报 `Too many query dimensions`。所以回源、命中率、域名明细在阿里侧是多次调用拼出来的。

还有一个隐蔽设定：ESA 响应里带 `SamplingRate`，低于 100 表示厂商侧采样。采样率不同的数据不能当平等数据比，面板会取最小采样率并在 UI 上标「≈」。

### 腾讯：不报错的错误最吓人

腾讯 EO 的坑是那个经典的「**返回全 0 且不报错**」。按域名取计量数据时，过滤键我一开始写了 `host`——接口正常返回 200，数据全是 0，没有任何报错。换成正确的 `domain` 之后，和站点级总量误差只有 0.0003%。这类错误如果没拿控制台对账，可能几个月都发现不了。

域名资产也有个坑：响应顶层键叫 `AccelerationDomains`，而不是想当然的 `AccelerateDomains`。以及后面要讲的那个大坑——**站点和域名是两回事**。

### Cloudflare：免费档就要有免费档的觉悟

CF 的限制最直白：免费档的 GraphQL **拿不到带宽字段**，legacy 的 analytics 接口已经下线（404, code 1015）。所以 CF 侧永远没有带宽峰值，只有区间流量。另外它的数据有 5–15 分钟延迟，且「今日」默认按 UTC 算——我拉小时桶回来按北京时间日界重新归日，否则 CF 的「今天」是从北京早上 8 点开始的。

## 口径：把三家拉到同一把尺子上

接口通了只是第一步，更大的问题是**三家的数字根本不可比**：

- **命中率**：腾讯控制台默认按请求算，官方公式是字节口径（1 − 回源响应流量 / 响应流量），阿里给的是 HIT 字节占比，CF 有 `cachedBytes/bytes`。最终统一成**流量字节命中率**（1 − 回源 / 流量），腾讯即官方公式，三家才站在同一把尺子上。这中间走过一次弯路：最早用请求口径，结果面板数字和三家官网都对不上，才意识到口径错了。
- **域名数**：阿里 `ListSites` 返回的 `mofashi.ltd` 是**站点**，不是域名；真实接入域名要再调 `ListRecords` 取子域名。腾讯侧同理，「站点级汇总 ≈ 其下全部域名之和」。最早腾讯域名显示 2 个，改完是 19 个——从「2」到「19」，就是从「把站点当域名」到「逐站点拉加速域名」的距离。
- **单位**：流量是字节，显示统一十进制 MB/GB（1000 进制），和厂商控制台一致。早期用 1024 进制显示带宽，被自己抓包对账时发现对不上。

所有口径公式集中在一个 `CdnMath` 类里，改口径只改这一处，并同步补单测。**口径散落在业务代码里，是数据类系统烂掉的最快方式。**

## 数字是怎么算错的：三个昂贵的故事

功能做完之后，我花了远比写功能更长的时间在「对账」上——拿面板和三家控制台逐项比。比出了三个故事，每个都值得单独讲。

### 故事一：凭空多出 21 倍的流量

厂商计量接口返回的是**当日累计计数器**的快照：早上 8 点返回「今日至今 1.2 GB」，晚上 8 点返回「今日至今 8.6 GB」，每天 0 点归零。面板每 5 分钟存一批快照，等我想看「最近 24 小时多少流量」时，第一版代码很自然地写了 `SUM(traffic_bytes)`。

结果数字大到离谱——把一天内几十批「越滚越大」的累计值加在一起，实测放大了约 **21 倍**。

解法是给表加**增量列**：每批快照落库时同时算出「本批新增了多少」，任意窗口的总量 = 增量之和。历史数据也全部回填重算。

### 故事二：回源流量比总流量还大

增量有了，第二个坑在回源。早期回源字节是用「累计流量 × 累计回源率」反推的估计值。问题是**累计回源率是个会浮动的平均值**：对它做差会出负增量，而当时「差值为负就用本行全额」的守卫逻辑，会把当天的回源重复累加。实测三家分别虚高：阿里 1.6 倍、Cloudflare 3 倍、**腾讯 26 倍**——仪表盘上出现过「回源大于出流量、命中率 0%」这种物理学奇观。

修复的原则从此定死：**字节量一律取厂商真实计数器**。腾讯有专门的回源接口（`l7Flow_inFlux_hy`，源站→节点响应流量），阿里用缓存状态维度的 MISS+BYPASS 字节，CF 用 `bytes − cachedBytes`。改完之后，面板数字和厂商控制台终于能逐项对上。

### 故事三：高水位线

增量怎么算，也有讲究。第一版用「本批累计 − 上一批累计」，很快被三类场景打脸：同时间戳的重复行让基线归零；一个序列里混进两个站点的数据导致累计来回跳；接口偶发抖动返回旧值。每一种都会造成重复计数。

现在的实现叫**高水位线**：增量 = 当前累计 − 同序列**同自然日内的最大累计值**，为负取 0。它带来一个可以程序断言的不变量——**任意一天的总量恒等于该日的最大累计值**。我按「厂商 × 粒度 × 名称 × 自然日」对全部 40 组序列断言过 `SUM(增量) == MAX(累计)`，零偏差。这意味着面板可以和厂商控制台「按日」逐项核对，而不只是「看着差不多」。

### 还有半个故事：粒度混用

最后一个坑不在算法在建模。腾讯常态只写**站点级**数据（每 30 分钟才补一轮域名级），阿里因为接口限制回源只能按站点取——于是库里有 `zone`（站点）和 `domain`（域名）两种粒度的行。**这两类行绝对不能混在一起求和**，站点级约等于其下全部域名之和，混着加等于双算。

更阴险的是「什么时候选什么粒度」。第一版是整个窗口统一选一次粒度，结果阿里的近 7 天视图从 1.53 GB 掉到 38 MB——因为阿里是某一天起才开始补写站点级行，「整窗选一次」把它更早的历史日整段过滤掉了。现在改成**逐自然日决定粒度**：当天有站点级行用站点级，没有就退回域名级。

这半个故事解释了前面那条橙色标注的由来：数据系统的边界条件太多，**与其假装没有边界，不如把边界如实画出来**。

## 只读是一条硬约束

面板是自用的，但我还是把「只读」做成了可验证的硬保证，而不是一句口号：

- 6 个开放 API 路由**全部只注册了 GET|HEAD**，实测 POST/PUT/PATCH/DELETE 一律 405；
- 令牌只存 sha256 哈希，明文只在生成时显示一次；无令牌 401，令牌访问管理页一律 302 跳登录；
- 控制器零数据库写操作，适配器零厂商写接口调用。

也就是说，**API 令牌就算泄露了，最坏结果也只是被读走数据，改不了任何 CDN 配置**。对一个拿着三家厂商密钥的系统来说，这个性质比什么都重要。

配套的还有一个细节：面板自己就挂在 EdgeOne 后面。有次翻 nginx 日志发现，直连源站 IP 的日志有 39 MB 全是扫描器打的 404，而域名日志只有 73 KB——反向印证了 EdgeOne 的命中率有 98.5%。CDN 管理面板被 CDN 保护着，算是一种职业福利。

## 运维侧的两记闷棍

数据对了之后，翻车改到运维侧。

**第一棍：全站 500。** 有次图省事用 root 跑了 artisan 命令，`storage/` 里留下了 root 属主的文件，php-fpm（www 用户）写不进去，整站 500。更烦人的是这事的隐蔽性：我 root 登上去跑 `artisan about` 一切正常，只有真实 HTTP 请求是 500。从此所有 php/artisan 操作固定降权到 www 执行，部署脚本里加了一键修属主的步骤。

**第二棍：还是全站 500。** `.env` 文件权限被改成了 `600 root:root`，php-fpm 读不到，Laravel 的 safeLoad **静默吞掉**加载失败——`APP_KEY` 为空，加密 Cookie 签不出来，还是全站 500。而 root 手动跑任何命令都正常。两记闷棍教会我同一条纪律：**排障必须以 web 用户的身份、走真实 HTTP 验证**，root 视角下的「一切正常」一文不值。

## 每天早上七点的 AI 日报

面板的数据自己不主动看的话，就只是一堆躺在 SQLite 里的存储占用。所以最后一块拼图是日报：每天早上 7 点，把**昨天一个完整自然日**的数据（含与前一天的环比）推送到我的邮箱，企微作为可选通道保留。

![](/img/posts/cdntool/settings-notify.webp)

推送正文里带一段 AI 分析。这块的关键洞察是：**模型本身不贵，难的是把喂给它的东西组织好**。

AI 输入从最初只有 863 字节的基础指标，扩到约 4660 字节——20 项扩展指标加 11 类分布维度，零新增采集（复用详情页已有的数据），另有 6000 字节的截断闸门兜底。但真正有价值的是三条实测换来的硬约束：

1. **每一行都必须带「厂商名｜」前缀。** 最初只在厂商块首行写名字，后续行靠缩进暗示归属——实测弱模型会把 Cloudflare 的威胁请求数算到阿里云头上。
2. **榜单合计不是全量，必须写明。** 不写的话，模型会拿 TopN 合计当总量算占比，得出一本正经的错误结论。
3. **缺项 = 该厂商不提供，不是采集故障。** 阿里没有耗时数据、CF 没有省份分布，不写明的话模型会「贴心地」帮你分析为什么采集坏了。

还有个反直觉的实测结果：对思考类模型（glm-4.6、qwen3.x），**关闭思考反而更快也更完整**——21.7 秒降到 4.9 秒，正文从空变成 124 字。原因是 reasoning token 和正文从同一份输出配额里扣，思考吃满了配额，正文自然就空了。「关闭思考 = 牺牲质量换速度」这个直觉，在这个场景下是反的。

## 收尾

现在的状态：三家 28 个域名、每 5 分钟一批快照、26 个测试用例守着口径公式和聚合逻辑，任意窗口的数字都能和厂商控制台对上账。

回头看，这个项目里最耗时的部分没有一行是「新功能」：21 倍的放大、26 倍的虚高、凭空消失的历史日——每一个数字错误的背后，都是我对「厂商到底给了我什么数据」的错误想象。做数据系统，一半的功夫在取数，另一半在**怀疑自己算出来的数**。

而「只读」这个从一开始就定下的约束，是整个项目里性价比最高的决定：它让所有的对账、重构、回滚都没有后顾之忧——大不了数字错了，反正什么都没碰坏。

剩下的事慢慢来：API 令牌的按厂商降权、源站回源段的访问限制、以及某个周末终将到来的 Laravel 升级。
