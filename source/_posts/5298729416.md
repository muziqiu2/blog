## 前言

做这个项目的起点很朴素：博客侧栏和几个自建页面都想放一张随机图。

一开始用的是别人搭建的公共二次元图 API，能用，但问题也很明显——要么限速，要么隔三差五换域名，要么图片挂在别人服务器上，哪天对方停了，我的页面就开天窗。图源不能自己掌控，这对我来说始终是个隐患。

于是就有了这个项目：一套图库完全由自己掌握的随机图片 API。现在的线上地址是 [sjtp.api.mofashi.ltd](https://sjtp.api.mofashi.ltd/)，代码全部开源在 [muziqiu2/img-api](https://github.com/muziqiu2/img-api)，采用 MIT 协议。

这篇文章记录一下它是怎么做出来的、长成了什么样，以及中间翻过的几次车。

## 它现在能做什么

先放一张功能总览，后面逐条说。

![](/img/posts/img-api/overview.svg)

### 三个入口，一套图库

图库在数据库里按渠道分成两类，对外则开三个入口：

- `api.php` —— 读 User-Agent 自动判断设备，是电脑就返回 PC 库的图，是手机就返回移动端库的图；
- `pc.php` —— 固定走 PC 库，不管访问者用什么设备；
- `pe.php` —— 固定走移动端库。

这样同一个地址可以直接丢进 `<img>` 标签用，也可以在需要精确控制时指定渠道。目前 PC 库有 551 张、移动端库有 996 张，合计 1,547 张。

### 两种出图模式

这个功能是被一个很实际的顾虑逼出来的：图存在我自己的图床上，302 跳转意味着任何人都能从浏览器地址栏、开发者工具甚至 F12 里直接看到原始图片地址。不是安全问题，但确实不想让图床链接被随便扒走。

所以在后台做了一个全局开关「图片访问模式」：

- **302 跳转模式**（默认）—— 返回一个 `Location` 头，浏览器自己去图床取图，服务器几乎零带宽压力；
- **代理模式** —— 由服务器 cURL 把图片拉回来再转发给访客，客户端拿到的始终是 API 域名下的地址，看不到真实来源。

两种模式的取舍很直白：302 省服务器带宽但暴露地址，代理隐藏地址但图片流量全部走自己的服务器。这套 API 的调用量不大，代理模式完全扛得住。

### 缓存与 JSON

除了直接出图，还有两个参数：

| 参数 | 说明 |
|------|------|
| `cache` | 缓存秒数，默认 0 不缓存。传 `cache=3600`，则一小时内重复调用返回同一张图 |
| `format=json` | 返回 JSON 而不是图片，方便程序二次处理 |

`format=json` 的返回长这样：

```json
{
    "success": true,
    "type": "pc",
    "mode": "redirect",
    "cache": 0,
    "url": "https://free-img.mofashi.ltd/.../xxxx.webp"
}
```

`cache` 参数在实际使用中比看起来有用——比如首页轮播图如果每次刷新都换一张，观感会很碎；设个缓存时间片，同一小时内保持稳定，到期自动换新。

### 后台与统计

管理后台是这套东西从「一个能跑的脚本」变成「一个能长期维护的服务」的关键：

- **图片管理**：增删图片链接、批量导入、按渠道分类；
- **操作日志**：谁在什么时候、从哪个 IP 做了什么；
- **网站设置**：站点名称、图片访问模式等均可改；
- **环境检测**：一键自检运行环境、PHP 扩展、目录权限；
- **系统更新**：基于 GitHub Releases 检查更新、一键升级、备份与回滚。

统计方面，每次调用都会按渠道计数并按天聚合，首页那张趋势图读的就是这份数据。

### 安全与部署

作为一个公网可访问、带后台的服务，安全这块不敢省：

- SSRF 防护：禁止访问内网 IP，校验 DNS 解析结果、图片 MIME 类型与文件魔数；
- CSRF Token、登录 5 次失败锁定 5 分钟、频率限制（API 每分钟 100 次、后台写操作独立限流）；
- 所有输入输出转义，敏感目录 `data/`、`admin/logs/` 禁止 Web 访问。

部署上给了 Docker 一键跑，另外附了一份 `nginx.conf.example`——因为项目自带的 `.htaccess` 只对 Apache 生效，用 Nginx 的话必须照抄那些 `deny all` 规则，否则 `data/app.db` 和备份压缩包可以被公网直接下载。这个坑我在 README 里特意加粗写了。

## 一次调用的完整链路

把上面这些串起来，一次 `GET /pc.php` 到底发生了什么：

![](/img/posts/img-api/flow.svg)

值得单独说的是第 5 步「存在性校验」。图库里的链接是外链，图床删了图、改了路径都是常有的事。所以出图前会做一轮校验：SSRF 检查、MIME 类型、图片魔数。其中 WebP 的魔数校验还踩了个坑——只看前 4 字节的 `RIFF` 是不够的，还得补验容器第 8-11 字节是不是 `WEBP`，否则一个 `.wav` 文件的前缀就能骗过校验。这类细节只有真的被绕过一次才会想到。

## 开发过程

![](/img/posts/img-api/timeline.svg)

### 阶段一：先让它出图

第一版（v2.0）简单得不像个"项目"：一个 `api.php`，从 SQLite 里随机取一条 URL，302 跳出去。没有后台，没有统计，图片靠手动往数据库塞。

但它当天就跑通了，而且验证了一件重要的事：**这套方案是成立的**——PHP + SQLite 的组合几乎在任何虚拟主机上都能跑，不需要 Redis、不需要 MySQL，备份就是拷一个文件。对个人项目来说，"零依赖"这个属性的价值远超性能。

### 阶段二：从"能用"到"能管"

接下来几天的迭代都围绕同一件事：让我不用连数据库就能维护它。批量导入、操作日志、密码和用户名修改（默认账号是 `admin` / `123456`，必须能改）、版本检查。

早期版本有个很典型的低级 bug：操作日志里所有记录的用户名都是空的 `[]`。原因是日志写入时机早于会话初始化，`$_SESSION['username']` 还不存在。这种问题测试时很容易漏掉——功能"正常"工作，只是数据悄悄缺失。

### 阶段三：被真实问题推着走

**坑一：一个 `rand` 参数打穿了整个 CDN。**

代理模式最初会给上游图片 URL 拼一个随机参数，本意是防止浏览器缓存住同一张图。结果这个参数直接破坏了图床 CDN 的缓存键——每一次请求都被判定为新资源，全部回源。表现是代理模式一出图，图床的流量就直线上升。

修法就是去掉它：代理模式下不该动上游 URL，要控制返回给客户端的缓存，用响应头 `Cache-Control` 就够了。

**坑二：Docker 镜像构建失败，报 `Cannot find config.m4`。**

一开始我以为基础镜像里缺 `pdo_sqlite`，于是在 Dockerfile 里手动 `docker-php-ext-install`。实际上基础镜像早就内置了该扩展，重复安装时的 `make clean` 把源码树清理了一遍，反而让后续编译找不到配置文件。

这两次翻车教给我的东西是一样的：**报错信息指向的位置，往往不是问题真正所在的地方**。以为是缓存问题，其实是缓存键；以为是缺依赖，其实是多装了一次。

**坑三：自动更新的回滚路径双重嵌套。**

在线更新这个功能写起来容易，写对很难。源码包解压出来的顶层目录名不一定是什么，需要在替换前把这一层"剥掉"，剥离逻辑写错就会变成 `a/b/b/` 这样的双重路径，回滚时直接找不到文件。

后来我把整个更新流程重写了一遍，补齐了并发锁、路径穿越检测、解压后目录名的兜底判定，并在更新成功后增加解压完整性、文件替换结果和版本号三重校验——因为还遇到过"更新实际失败，界面却提示成功"的问题。**一个会骗人的更新按钮，比没有更新按钮更危险。**

### 阶段四：拆开重构

代码量涨到一定程度后，`config.php` 变成了一个什么都往里塞的巨型文件。最近一轮重构把它收敛成纯粹的配置入口，业务函数按职责拆进 `lib/` 下的独立模块（`db` / `auth` / `images` / `network` / `stats` / `update` / `ratelimit` / `settings` / `cache` / `log` / `version` / `environment`），后台各功能区块也拆成了 `admin/views/` 下的子视图。

这次重构最有价值的产出其实不是文件变整齐了，而是**它证明了前面几个月的安全意识是可以继承的**——拆模块的过程逼着我重新读了一遍每个函数，顺手又清掉了几个当时没注意的边界情况。

## 数据说话

截至写这篇文章，站点首页的统计是这样的：

![](/img/posts/img-api/trend.svg)

几个数字：累计调用约 **12.5 万次**，近 30 天日均约 500 次，单日峰值出现在 8 月 26 日的 **2,660 次**。

趋势图里有几个明显的尖峰，基本对应两种情况：一是我自己在调试（比如 8 月中旬那几天），二是被某个页面引用后集中请求。8 月下旬之后曲线回落并趋于平稳，日均 100 次左右，这正是"给几个自建站点当配图源"该有的量级。

我最满意的一点是：**这些数字是自动长出来的**。统计是每次调用顺带完成的，趋势图是读同一份数据渲染的，不需要我额外维护任何报表。

## 怎么接入

最简用法，一行搞定：

```html
<img src="https://sjtp.api.mofashi.ltd/api.php" alt="随机图片">
```

需要指定渠道或加缓存：

```html
<!-- 固定 PC 库，缓存 1 小时 -->
<img src="https://sjtp.api.mofashi.ltd/pc.php?cache=3600" alt="随机图片">

<!-- 固定移动端库 -->
<img src="https://sjtp.api.mofashi.ltd/pe.php" alt="随机图片">
```

在代码里当接口用：

```bash
# 直接 302 跳转
curl -I https://sjtp.api.mofashi.ltd/pc.php

# 拿 JSON
curl "https://sjtp.api.mofashi.ltd/pc.php?format=json"
```

## 开源与后续

仓库在 [muziqiu2/img-api](https://github.com/muziqiu2/img-api)，MIT 协议，可以自由使用、修改乃至商用，保留版权声明即可。如果你也想搭一套自己的随机图服务，直接下载 Release 包丢到服务器就能跑，环境要求只有 PHP 7.4+ 和 PDO SQLite 扩展——基本上是个 PHP 空间都满足。

后面想做的事：

- 图库自动去重与失效链接巡检，现在校验是出图时做的，希望能提前批量发现坏图；
- 多渠道容灾，单一图床挂了能自动切到备用源；
- 更细的统计维度，比如按来源 Referer 或按具体接口分开看。

从 6 月 14 日第一次提交到现在，这个项目走过了 142 次提交。它没什么高深的技术，但把一个真实需求从"能跑"打磨到了"能长期跑"——对我个人来说，这可能比写一个更酷的项目更有意义。
