## 前言

魔法师图床（[tc.mofashi.ltd](https://tc.mofashi.ltd/)）是我在兰空图床（Lsky Pro）基础上二次开发并长期运营的公益图床。它一直在跑，也一直"能用"——但"能用"和"好用"之间，隔着一段我拖了很久没去动的地带。

真正让我下决心动手的，是三个各自独立、又都挺刺眼的问题：

1. **首页的体验其实很差**。首屏要加载约 1.68 MB，其中大部分是被浪费掉的；主标题用了浅灰渐变文字压在明亮的插画上，几乎读不出来；hero 区写死了整屏高度，真正的正文内容全在首屏之外。更细一点的问题还有：首页根本没有登录入口，页脚被塞在最后一个展示区块内部，两个装饰光斑因为样式失效而完全不显示。
2. **压缩策略只覆盖了一半用户**。当时只有游客上传会自动压缩，登录用户反而不压缩。这既不合理，也浪费存储——对一个免费图床来说，存储是真金白银。
3. **长图会被压缩成马赛克**。旧规则是把整张图塞进一个 `1920×1920` 的方框，一张 `10000×1000` 的宽幅长图压完只剩 `1920×192`，短边不到 200 像素，字都糊成一团。

这三个问题分别对应三类工作：**视觉体系对齐、交互策略调整、图像处理算法重做**。下面按这个顺序说。需要说明的是，站点首页是静态的 `public/index.html`，上传页是 Blade 渲染的动态页，两者的改动与上线流程并不一样，这点后面会单独讲。

## 一、首页：先解决「看得下去」

### 1.1 先定基准：向主程序对齐，而不是另起一套

重构之前要回答一个前置问题：**新的首页该长什么样？**

一开始我考虑过参考站点里的独立上传页 `upload/index.html`，因为它自己有一整套样式。但这个方向很快被否掉了——它是全站唯一一个风格与其他页面完全不同的存在。真正有"强制力"的视觉语言在主程序本体：`resources/css/common.less` 里定义的那套企业简洁体系——底色 `#f7f8fa`、品牌蓝 `#2563eb`、细描边、`8/10/12px` 三级圆角、**不用渐变和发光**。

它之所以是基准，是因为它管着后台、登录页、上传页所有页面，甚至用 `!important` 把各种杂色统一压成品牌蓝。**首页才是那个违和的例外**，而不是别人应该向首页看齐。

顺带澄清了此前的两个误判：`Nunito` 字体在整个项目里只声明、从未加载；导航里的 `/user/images` 是 JSON 接口而不是页面，入口必须写 `/images`。

### 1.2 一个绕不开的约束：不可重建的 Tailwind 子集

真正决定技术路线的是这个发现：

站点引用的 `public/static/css/main.css`，是 **Tailwind v3.0.23 的 JIT 编译产物，只有 232 条规则**，而且是**不可重建的**——`tailwind.config.js` 的 `content` 里不包含 `public/*.html`，本地也没有 `node_modules`。

这意味着：在首页里写任何新的 Tailwind 类名，**都不会有任何效果，而且不会报错**。它会静默失效。

所以最终方案是**单文件自包含**：样式全部内联在 `index.html` 里，不再引 `main.css` 和 `alpine.js`，需要什么手写什么。同时把结构补齐：`<header>` / `<nav>` / `<main>` / `<footer>` 加跳转到主内容的 skip link，零处内联 `style=`，并补上了此前完全没有的**登录入口**。

### 1.3 首屏 1.68 MB → 118 KB

砍掉 alipine 与各类冗余资源之后：

![](/img/posts/mofashi-imgbed/home-after.webp)

对比一下优化前——满屏壁纸，渐变标题几乎读不出来，正文全在首屏之外：

![](/img/posts/mofashi-imgbed/home-before.webp)

首屏体积从 **1.68 MB 降到 118 KB**，下降了 93.3%。拆开看，钱花在了四个地方：`alpine.js` 77 KB 直接去掉、logo 从 562 KB 换成 28 KB、favicon 从 533 KB 压到 6 KB、首屏插图从 544 KB 减到 75 KB。

## 二、压缩开关：从「只对游客」到「统一可开关」

### 2.1 改一处，两端生效

压缩逻辑写在 `resources/views/components/upload.blade.php` 里，而游客上传页和登录用户上传页**引用的正是同一个组件**。也就是说改这一个文件，两端同时生效——这是个好消息，也是一个必须确认的前提（核对过全部路由，管理后台没有上传入口）。

改造的核心是把两件事拆开：

- `canCompress(file)` —— **客观能力**：格式是否可压、体积是否值得压、浏览器是否支持 WebP、以及**该用户所属组是否接受 webp 后缀**；
- `compressEnabled` —— **主观意愿**：用户这次要不要压。

原来的代码把这两件事混在一个 `isGuest` 分支里，所以才会出现"游客压、登录不压"这种跟能力无关、纯由身份决定的行为。

### 2.2 一个刻意的取舍：默认开启，但不持久化

关于开关的默认状态，我最后选的方案不是"记住用户选择"，而是：

**每次加载默认开启，只对当次访问有效，不做任何持久化**——不写 `localStorage`，不写 `sessionStorage`，也不写账号配置。刷新页面就回到默认开启。

这个选择看起来有点奇怪，但权衡是清楚的：这是公益图床，存储成本由我承担，我希望默认能省一点；但我又不想用"记住你关掉了"的方式把用户绑死在一个选择上——他每次来都可以重新决定。**所以这是一个有意为之的取舍，而不是漏了持久化。**

线上实际长这样——上传卡片顶部多出一条开关条，右侧是开关状态：

![](/img/posts/mofashi-imgbed/compress-ui.webp)

配套的还有三处状态提示联动：开关条本身、拖拽区副标题、以及上传卡片上的体积对比（形如 `3.2 MB → 786 KB · 省 76%`）。

真正麻烦的是**切换开关时的状态机**。已经进入传输队列的项不能随便重来——直传模式下的 `presign` 签名里绑定了文件体积，中途把原图换成压缩图会让签名校验失败。所以做了三件事：`renderToken` 用来丢弃已经过期的异步结果；`started` 标记保护已在传输中的项；`pending` 标记防止「全部上传」把还没替换完的原图提交出去。最后统一收敛到一个提交入口 `submitItem(guid)`。

## 三、压缩链路：把「静默失效」逐个堵上

### 3.1 Safari 的 WebP 谎言

压缩用的是浏览器原生的 canvas 能力。这里踩了一个很隐蔽的坑：

**Safari 上调用 `canvas.toBlob(cb, 'image/webp')`，不会失败，也不会报错，它会安安静静地返回一张 PNG。**

如果不做校验，代码会以为"WebP 压缩成功"，然后把一张伪装成 WebP 的 PNG 交出去——要么被服务端按后缀拒收，要么白白浪费一次"压缩"。

解法是**回验**：拿到 blob 之后检查 `blob.type` 是否真的等于请求的 MIME，不相等就说明浏览器不支持，降级到 JPEG。因此压缩的候选链是 `[webp, jpeg]` **逐级尝试**，而不是只押注 WebP。

### 3.2 并发与白底

另外两处：

- **JPEG 没有 alpha 通道**。带透明区域的图直接转 JPEG，透明部分会变成黑色。所以编码前先铺一层白底。
- **并发要限流**。同时解码+编码十几张大图，在低端手机上会把主线程压死，页面直接假死。所以把并发上限设为 2。

再加上两条基础规则：质量系数 `0.65`，体积原本就小于 100 KB 的图直接跳过（小图重压几乎没收益，还会损失画质）。

## 四、缩放规则：从「方框」到三级约束

### 4.1 方框的问题

旧逻辑是"整图塞进 `1920×1920` 方框"——取长边缩放到 1920，另一边按比例。对 4:3 的照片没问题，但对极端长宽比就是灾难：

`10000×1000` 的图（10:1），长边缩到 1920，短边只剩 **192 像素**。

### 4.2 targetSize() 的三级约束

新写的 `targetSize()` 用三级约束替代方框：

1. **常规长边 ≤ 1920** —— 普通照片的尺寸与体积完全不变（比如 `4032×3024` → `1920×1440`）；
2. **短边保底 720** —— 如果原图短边本就不足 720，那么不对它打折，等价于"只压画质、不缩尺寸"；
3. **安全天花板** —— 总像素 ≤ 12MP、单边 ≤ 8192。

第三条不是拍脑袋定的。**iOS 的 canvas 上限大约在 16.7MP**，超过这个尺寸的 canvas 不会报错，而是**只给你一张全白画布**。所以必须主动设一个安全线，宁可少缩一点，也不能拿到白图。

配套的细节还有：`probeImageSize()` 先量出原图尺寸再决定策略，**量不出来就按原图上传**（不猜）；缩放用 `downsamplingRatio: 0.5` 配合 `imageSmoothingQuality: 'high'`；目标尺寸取 `Math.ceil` 而不是 `Math.round`——用 round 时 `1080×8000` 会落到 `719×5333`，短边就跌破 720 了。

### 4.3 实测对比

用完全相同的原图跑新旧两套逻辑：

![](/img/posts/mofashi-imgbed/scale-compare.webp)

| 原图 | 旧规则（1920 方框） | 新规则（三级约束） |
|---|---|---|
| 10000×1000 | 1920×**192** · 9 KB | 7200×**720** · 747 KB |
| 6000×1000 | 1920×320 | 4320×720 |
| 1080×8000 | 259×1920 | 720×5333 |
| 4032×3024 | 1920×1440 | 1920×1440（不变） |

注意最后一行：**常规比例的照片，新旧结果完全一致**——这次重做只针对长宽比异常的图，没有牺牲普通用户任何画质。

## 五、文案与窄屏：把像素账算清楚

压缩提示的文案最初写得很细，桌面上看没问题，手机端却把卡片撑得很难看。于是做了两件事。

**一是精简文案**：开关条标题从「上传前自动压缩」缩短为「上传前压缩」，描述从「转为 WEBP 减小体积，小于 100KB 的图片自动跳过」砍成「自动减小体积，小图跳过」；删掉拖拽区那一行与开关条重复的提示；体积行里的「· WEBP」后缀也去掉了（格式名不再对用户露出）；进行中的提示做成「处理中 3/5」这种带进度的形式。

**二是加断点收起次要元素**：`414px` 以下收起状态徽标，`360px` 以下连装饰图标也收掉。

![](/img/posts/mofashi-imgbed/compress-copy-compare.webp)

这里有个教训值得记一下。第一轮我用**自搭的测量页**得出结论「414 断点之后 360~430px 全部单行」——**这个结论是错的**，因为自搭页面没有还原真实的容器宽度。改成抓线上真实页面后才发现：宽度被三层内边距吃掉了 128px（`main` 的 `px-5` 40px + 卡片的 `p-6` 48px + 内层的 `p-5` 40px，再加上条自身的内边距）。320px 视口下，文案区实际只剩 **56px**，标题被迫折成两行、描述三行，整条高 110px。

改完再在线上实测 8 档视口（320/340/360/375/390/414/430/500）：

![](/img/posts/mofashi-imgbed/compress-narrow.webp)

**全部是「标题 1 行 + 描述 1 行」，折行条数 0。** 360\~430px 区间条高统一 58px，320px 下因为文字本身就窄，是 75px——但标题和描述都不再折行。

## 六、优化前后对比

汇总一下这次改动的结果：

| 项目 | 优化前 | 优化后 |
|---|---|---|
| 首页首屏体积 | 1.68 MB | **118 KB**（−93.3%） |
| 首页 `alpine.js` | 77 KB | 0（移除） |
| logo | 562 KB | 28 KB |
| favicon | 533 KB | 6 KB |
| 首屏插图 | 544 KB | 75 KB |
| 首页登录入口 | 无 | 有 |
| 压缩开关 | 仅游客，无 UI | 游客/登录统一，可见开关 |
| Safari WebP | 静默返回 PNG | 校验后降级 JPEG |
| 缩放规则 | 1920×1920 方框 | 长边 1920 / 短边保底 720 / 12MP 天花板 |
| 10000×1000 的图 | 1920×192·9 KB | 7200×720·747 KB |
| 压缩条窄屏排版 | 320px 下整条 110px、标题折行 | 58px、单行 |
| 生产目录体积 | 149 MB | 112 MB（释放 37 MB / 3143 个 inode） |

最后一行是同期做的一次生产环境清理：`storage/temp/` 里躺着一个 2022 年中断的在线升级残包（35 MB），加上 61 个编译视图、13 个历史日志、旧的 bootstrap 包缓存等，一共释放了 37 MB。**这一步严格限定在图床目录内，项目之外的路径一律没动。**

## 七、上线路上翻的两次车

静态首页和动态上传页的发布方式不同，这也是这次踩坑的背景。

**首页是静态文件**，而且在腾讯云 EdgeOne 后面——**裸 `/` 是被边缘缓存的**，而 `/index.html` 和带查询串的 `/` 是另外的缓存键。所以流程固定为：部署 → 刷一次根 URL → 验收。注意探测本身会污染缓存：第一次 `MISS` 会把当时的内容写进边缘并重置 TTL，**所以部署前不要先去 curl 线上首页**。至于 `/index.php` 这类动态页，响应头本来就是 `Cache-Control: private, no-cache`，压根不进缓存，改了就只做"部署 → 清视图缓存 → 验收"。

真正把线上打挂的是另一件事。

**第一次 500：Blade 把 `{{` 当成了模板输出。** 我在 JSDoc 注释里写了一句：

```js
/** @returns {{width:number, height:number}|null} null 表示无需缩放 */
```

Blade 编译器把 `{{` 识别为模板输出起点，一路吞到后面某个 `}}`，编译出来的 PHP 成了 `<?php echo e(width:number, height:number}|null} …`，直接 `Parse error`，**整个上传页 500**。更麻烦的是本地那道 JS 语法闸门抓不到它——因为闸门会先把 `{{ }}` 替换掉，替换动作恰好掩盖了冲突。

修复很简单（改成单花括号的 `{Object|null}`），但暴露了一个流程问题：**这次是"先覆盖线上、后检查"，所以线上 500 了几十秒。正确顺序是先把候选文件传到临时路径过一遍编译闸门，确认通过再覆盖线上。** 我把这个动作固化成了脚本，现在每次改 Blade 都要先过闸门。

**第二次：并发编辑丢改动。** 同一个文件里的「HTML 文案」和「JS 文案」两处修改在同一批发出去，两次写入各自基于旧内容，后写覆盖了先写。工具回显都是成功，但改动实际上不在文件里。线上之所以看起来正常，是因为 JS 在运行时又把文案覆盖了一遍，把问题藏住了——最后靠部署后 grep 线上页面才发现。

所以现在有条规矩：**同一文件的多处修改要么串行、要么整份重写；部署后必须 grep「新文案在、旧文案 0 处」，不能只信编辑回执。**

## 八、后续方向

这次改动不算小，但清单上还有明确没做的：

- **极端宽高比的取舍**。现在 20:1 这种比例会止步于安全天花板（比如 `8192×409`），这是 iOS canvas 上限决定的，短期没有更好的解法，只能继续"接受它比现在好得多"。
- **独立的 `upload/index.html` 上传页**仍是它自己那套基于 `localStorage` 的旧压缩逻辑，没跟着这次改造走。归属还没定：要么同化，要么废弃。
- **暗色模式**目前故意不做——主程序企业简洁体系是浅色单套，硬加暗色反而会把一致性搞乱。
- **压缩率还可以再挑**。现在 `0.65` 的质量系数对照片是够的，但对带文字的长截图可能偏狠，后面考虑按内容类型分档。

回过头看，这次三块工作的共同点其实是同一个：**先把"看起来正常"和"真的正常"区分开**。首页看起来能用，但首屏 67% 是浪费；压缩看起来生效了，但 Safari 上悄悄退成了 PNG；缩放看起来在做缩放，但长图已经糊了。

把这三件事逐一量出来，改动方向也就没什么可犹豫的了。
