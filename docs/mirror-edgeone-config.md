# 镜像站 EdgeOne 配置方案 · cdn-jsdelivr.mofashi.ltd

> 对象：自建 jsDelivr 镜像 `cdn-jsdelivr.mofashi.ltd`（前方 = 腾讯云 EdgeOne，源站 = 你自建的转发服务）
> 实测时间：2026-09-12
> 本文只讲**怎么点/怎么设**，不涉及任何 JSON 格式的配置语法。

---

## 一、先摆事实：三行实测结论

| 取值路径 | 结果 |
|---|---|
| **回源**（给 URL 加随机查询串 `?cb=xxx` 强制回源） | 完整、与官方逐字节一致 ✅ |
| **命中缓存**（`pace-js@1.2.4`、`fontawesome-free@7.3.0/css`） | 被截断（12962→4676、90169→22948）❌ |
| **命中缓存**（新换一个从未请求过的包版本，三种 Accept-Encoding 各取一次） | 全部完整 ✅ |

⇒ 结论：**回源没问题，现在也不再产生新的坏副本；坏的只是缓存里那 2 条历史遗留。**
所以下面第 1 步是必须做的，第 2、3 步是防它再次发生。

---

## 二、第 1 步：刷掉坏副本（必做，5 分钟）

控制台路径：**站点 `cdn-jsdelivr.mofashi.ltd` → 站点加速 → 缓存配置 → 刷新缓存**

- 刷新方式选 **按 URL 刷新**（不要选"按目录刷新 `/npm/`"，那会把整个镜像的缓存清空、回源压力极大）
- 粘贴这两条（就是全部存量坏条目）：

```
https://cdn-jsdelivr.mofashi.ltd/npm/pace-js@1.2.4/pace.min.js
https://cdn-jsdelivr.mofashi.ltd/npm/@fortawesome/fontawesome-free@7.3.0/css/all.min.css
```

> 为什么必须手动刷：这两个响应带 `Cache-Control: public, immutable, max-age=31536000`，
> 坏副本**一年之内不会自愈**，用户普通刷新甚至 F5 都无效。

刷完在仓库根目录跑一次自检，看到「全部正常 ✅」即通过：

```bash
node tools/mirror-check.mjs
```

---

## 三、第 2 步：改 5 个开关（防复发）

路径：**站点 → 站点加速 → 缓存配置**（站点级全局设置）

| # | 设置项 | 改成 | 为什么 |
|---|---|---|---|
| 1 | **节点缓存 TTL** | 由「遵循源站」改为 **自定义 → 604800 秒（7 天）** | 源站（jsDelivr 经 Cloudflare）给的是 `max-age=31536000`。跟着源站走 = 坏副本活一年；改 7 天 = 最坏情况一周内自愈 |
| 2 | **浏览器缓存 TTL** | 改为 **自定义 → 86400 秒（1 天）** | 同上，缩短坏副本在用户浏览器里的存活时间 |
| 3 | **`immutable` 必须删掉** | 见下方"如何删" | `immutable` 让浏览器**连条件请求都不发**，坏了就永远坏 |
| 4 | **查询字符串参与缓存键** | 保持「全路径缓存」= 开启（若界面写作「忽略查询字符串」→ **关闭**） | 应急绕过手段 `?v=日期` 依赖它；实测该镜像的缓存键**已包含**查询串，别改坏 |
| 5 | **智能压缩** | 保持 **开启**（brotli + gzip） | 镜像站靠它省流量；它本身不是这次故障的原因 |

**其余保持默认即可**：`Vary` 策略（实测 `vary: Accept-Encoding` 是生效的，三个压缩变体各自独立缓存，别动）、
离线缓存开启、缓存预刷新开到 90%（提升回源命中）。

### 如何删掉 `immutable`

`Cache-Control: public, immutable, max-age=31536000` 是**上游透传**过来的，缓存配置页改不了它。
在 **站点加速 → 规则引擎** 里加一条规则，动作选「**修改响应头**」：

- 操作：**替换**（或 先"删除 `Cache-Control`" 再"添加 `Cache-Control`"）
- 响应头名：`Cache-Control`
- 值：`public, max-age=86400`

加这一条就够，不用像博客站那样按后缀分好几条——**镜像站的 URL 天然带版本号**
（`/npm/<pkg>@<version>/<file>` 内容不可变），一刀切的策略是安全的。

## 四、第 3 步：回源侧堵住源头（治本，最省事的一招）

路径：**站点 → 站点加速 → 回源配置 → 回源请求头**

新增一条固定请求头：

| 名称 | 值 |
|---|---|
| `Accept-Encoding` | `identity` |

**作用**：让回源永远拿到**未压缩的完整明文**，缓存里存的就永远是完整实体，
从源头消灭"压缩长度 / 明文长度不一致"这类问题；对客户端的压缩仍然由边缘按
`Accept-Encoding` 现场做，访问速度不受影响。

这一步和「针对漏洞本身打补丁」相比，**成本最低、收益最大**，建议一定要加。

---

## 五、如果镜像源站是你自己的边缘函数 / Worker

回源代码里对照检查两点（这两点是本次截断能"落进缓存"的根因）：

1. **回源请求固定 `accept-encoding: identity`**，不要在转发时透传客户端的压缩头。
2. **不要把上游给的 `Content-Length` 原样透传**：
   - 如果你自己解压过 body，必须**同时删掉 `Content-Encoding` 和 `Content-Length`**；
   - 如果是流式转发，务必保证 body 完整——**最稳的做法是先把 body 读成完整 Buffer 再一次性返回**，
     半截的流 + 看似匹配的长度，会被边缘当成"正常响应"缓存下来（这次就是这么坏的）。

改完记得再刷一次那两条 URL 的缓存做验证。

> 注：如果暂时不想改回源代码也没关系——第 2、3 步的配置已经足够防复发；改代码只是让根因消失。

## 六、验收

1. 刷缓存后跑自检：

```bash
node tools/mirror-check.mjs          # 期望：全部正常 ✅，退出码 0
```

2. 手动确认某一条（两种压缩姿势都要对）：

```bash
unset HTTP_PROXY HTTPS_PROXY http_proxy https_proxy
U="https://cdn-jsdelivr.mofashi.ltd/npm/pace-js@1.2.4/pace.min.js"
curl -sS -o a.bin "$U"                       # 无 Accept-Encoding
curl -sS --compressed -o b.bin "$U"          # 带压缩
wc -c a.bin b.bin                            # a 应为 12962；b 解码后也应为 12962
```

3. 确认新 TTL 生效：随机挑一个新 URL 连取两次，第二次 `eo-cache-status` 应为 `HIT`，
   且带/不带压缩头两次的**解码后内容一致**。

---

## 七、三条红线

1. 🔴 **不要给这个站点开 `immutable` / 一年 TTL** —— 坏副本一年不自愈，这正是本次踩的坑。
2. 🔴 **不要"按目录刷新 `/npm/`"** 来图省事 —— 缓存全空，回源会被打爆；只刷具体坏 URL。
3. 🔴 **回源请求头不要透传客户端的 `Accept-Encoding`** —— 固定 `identity`，别让它变成压缩体入库。
